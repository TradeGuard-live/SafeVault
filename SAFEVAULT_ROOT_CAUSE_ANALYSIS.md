**Application**: SafeVault (Personal Document Manager, Bank Vault & Password Manager)  
**Classification**: ENGINEERING ROOT CAUSE ANALYSIS & ARCHITECTURAL MITIGATION  
**Date**: November 2026  
**Auditor**: Senior Software Architect & Android Security Specialist

## 1. ROOT CAUSE 1: HARDWARE KEYSTORE VS SOFTWARE KEK STORAGE

### Architectural Flaw Description
In earlier versions, the biometric key share $S_{bio}$ was stored in `flutter_secure_storage` wrapped by an AES key (`_keyBioKek`). Although `flutter_secure_storage` uses Android Keystore internally to encrypt its key-value pairs, it did not configure the key with `setUserAuthenticationRequired(true)`.

### Impact & Exploitation Vector
An attacker on a rooted device or utilizing Frida dynamic binary instrumentation could invoke the secure storage decryption method directly from userspace, bypassing Android's native `BiometricPrompt` and recovering $S_{bio}$ without physical biometric authentication.

### Root Cause Resolution
Architected a dedicated platform channel `com.vault.security/keystore_biometric` in `MainActivity.kt`:
1. Directly invokes Android Keystore Keymaster / StrongBox with `KeyGenParameterSpec.Builder("vault_biometric_hardware_kek", ...)`.
2. Configured:
   - `setUserAuthenticationRequired(true)`
   - `setUserAuthenticationParameters(30, KeyProperties.AUTH_BIOMETRIC_STRONG)`
   - `setInvalidatedByBiometricEnrollment(true)`
3. Enforces that hardware unwrapping of $S_{bio}$ strictly requires an authorized cryptographic token generated by Android's hardware `BiometricPrompt`.
4. If a device PIN is changed or new fingerprint enrolled, Android Keystore permanently invalidates the key (`KeyPermanentlyInvalidatedException`), mitigating physical device theft scenarios.

## 2. ROOT CAUSE 2: ACTION REDIRECTION (DASHBOARD REDIRECT BUG)

### Behavioral Flaw Description
When a user triggered a protected action on a detail screen (such as revealing a bank account number, revealing a password, deleting a document, or restoring from trash), 2FA verification was requested. Upon passing verification, the app router unconditionally executed:
```dart
context.go('/dashboard');
```
The user's screen state, target record ID, and requested action were destroyed.

### Root Cause Analysis
The redirect logic in `app_router.dart` only checked whether `isUnlocked` transitioned from false to true. Lacking a central coordination mechanism, it possessed no awareness of where the user came from or what operation was pending.

### Root Cause Resolution
1. Created `AuthenticationGate` with a structured `PendingVaultAction` queue:
   ```dart
   class PendingVaultAction {
     final String id;
     final VaultActionType type;
     final String? targetId;
     final String? targetName;
     final String originalRoute;
     final String returnRoute;
     final Map<String, String>? queryParams;
     final Map<String, dynamic>? safeState;
     final DateTime createdAt;
   }
   ```
2. Updated `AppRouter.redirect`: upon unlock, the router checks `gate.pendingAction?.returnRoute`. If present, it restores the deep route (e.g. `/bank-account/123`, `/document/456`) instead of navigating to `/dashboard`.
3. Added single-execution guarantee: `consumePendingAction(targetId)` ensures an action executes exactly once for its intended target and discards expired actions (> 5 minutes).

## 3. ROOT CAUSE 3: STORAGE ACCESS FRAMEWORK (SAF) LIFECYCLE LOOP & FORM ERASURE

### Behavioral Flaw Description
When opening Android's native system file picker (`ACTION_OPEN_DOCUMENT`), the host activity transitioned to `inactive` / `paused`. The vault locked immediately, and when the user returned with the chosen file, the form was reset and all typed metadata was lost.

### Root Cause Analysis
Multiple `VaultScaffold` widgets registered duplicate `WidgetsBindingObserver` listeners. Each listener responded to `AppLifecycleState.paused` by invoking `session.lockVault()` immediately, without checking whether the user had intentionally launched an Android system activity.

### Root Cause Resolution
1. Implemented `VaultSession.beginSystemActivity(activityType, timeout: Duration(minutes: 5))` and `endSystemActivity()`.
2. In the root `AppLifecycleListener`, auto-locking is suppressed while `isSystemActivityActive` is true.
3. Added an independent 5-minute bounded lease timer: if an external activity fails to return or crashes, the lease automatically expires and the vault locks safely.
4. Added concurrency guard `_isPicking` in `NativeSafAndShareService` to prevent duplicate picker intents.
5. Implemented encrypted auto-draft saving and restoration in `AddDocumentScreen`.

## 4. ROOT CAUSE 4: INCOMPLETE VEHICLE RC EXTRACTION & REGEX PRECEDENCE

### Extraction Flaw Description
Vehicle RC Books failed to extract Vehicle Manufacturer, Vehicle Model, Colour, and Cubic Capacity. Furthermore, the owner name was frequently extracted incorrectly (e.g. capturing `REGISTRATION DATE` as the owner name).

### Root Cause Analysis
1. Extractor lacked exact aliases for Indian RC documents (e.g. `VEHICLE MANUFACTURER`, `VEHICLE MODEL`, `COLOUR`, `CUBIC CAPACITY`).
2. The owner name extractor checked next-line matches (`i + 1`) before checking same-line matches. In standard RC cards where the label and value appear on the same line, the next-line check ran first and captured subsequent label headers as names.

### Root Cause Resolution
1. Added all required aliases to `DocumentFieldExtractor`.
2. Inverted line-search logic: evaluates same-line regex with `_isValidName` first; only checks line $i + 1$ if no valid same-line match exists.
3. Verified extraction of all 14 RC book fields in automated test suite.

## 5. ROOT CAUSE 5: ANDROID 13+ EXACT ALARM CRASHES

### Behavioral Flaw Description
Creating an expiry reminder on Android 13+ devices threw `PlatformException(exact_alarms_not_permitted)`.

### Root Cause Analysis
Android 13 (API 33+) introduced strict restrictions on `SCHEDULE_EXACT_ALARM`. Calling `zonedSchedule` with `AndroidScheduleMode.exactAllowWhileIdle` without holding the user-granted exact alarm permission causes Android OS to throw an unhandled security exception.

### Root Cause Resolution
Wrapped `LocalNotificationService.scheduleExpiryReminder` with `canScheduleExactNotifications()` check. If exact alarms are not permitted by device policy, it gracefully falls back to `AndroidScheduleMode.inexactAllowWhileIdle`, ensuring reliable reminder scheduling without crashing.
